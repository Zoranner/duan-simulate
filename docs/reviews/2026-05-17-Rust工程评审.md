# DUAN Rust 工程评审报告

## 评审范围

本次只评审 DUAN 仓库的 Rust 工程体系、crate 边界、依赖治理、质量门禁、文档同步和长期维护风险，不评价功能需求完成度、业务规则正确性或单个 bug。

仓库根目录当前是产品与文档集合，不是 Cargo package 或根 Cargo workspace。评审时按父仓文档、各 `packages/*` 子模块和 `examples/packages/*` 示例包的当前事实分别检查。

## 评审依据

- `review-engineering` 通用工程基线：目录边界、验证入口、产物治理、文档与代码一致、提交可追溯。
- `review-rust` Rust 专项基线：Cargo 边界、features、错误处理、unsafe、依赖治理、fmt、clippy、test、build、doc。
- 用户与仓库规则：中文输出；Rust 修改后必须执行 `cargo fmt --all` 与 `cargo clippy --all-targets --all-features -- -D warnings`；评审只读阶段优先使用检查命令。
- 仓库文档：`README.md`、`docs/architecture.md`、`docs/platform-design.md`、`docs/package-naming.md`、`docs/package-authoring.md`、`.gitmodules`、`.gitignore`。

## 总体结论

当前主要 Rust crate 和示例包能够分别通过格式、clippy、测试、构建和文档生成检查，没有发现编译 warning、clippy warning、native build script、FFI、async runtime 混用或已跟踪构建产物污染。

工程风险集中在跨 crate 级别：父仓明确不作为 Cargo workspace，但也缺少等价的聚合验证入口；这会让跨 `duan` facade、runtime、catalog、runner、build、CLI 与 examples 的变更依赖人工逐包执行。其次，runtime/catalog/runner 仍存在面向作者或执行宿主可触发的 panic/`expect` 边界，错误类型保真度不一致。文档方面，少量入口文档和归档计划仍保留过时迁移状态或可执行指令语气。

## 检查情况

- `cargo fmt --all -- --check`：已逐包执行，覆盖 `packages/duan`、`packages/duan-core`、`packages/duan-catalog`、`packages/duan-scenario`、`packages/duan-runner`、`packages/duan-build`、`packages/duan-cli`、`packages/duan-macros`、`examples/packages/free-fall/*`、`examples/packages/naval-combat/*`，全部通过。
- `cargo clippy --all-targets --all-features -- -D warnings`：同上逐包执行，全部通过。
- `cargo test --all-targets --all-features`：同上逐包执行，全部通过。`packages/duan-core` 的 `--all-targets` 会同时运行 Criterion bench target 的测试模式，输出 `Testing ... Success`。
- `cargo build --all-targets --all-features`：同上逐包执行，全部通过。
- `cargo doc --all-features --no-deps`：已对主要框架库执行，覆盖 `packages/duan`、`packages/duan-core`、`packages/duan-catalog`、`packages/duan-scenario`、`packages/duan-runner`、`packages/duan-build`、`packages/duan-macros`，全部通过。
- `git submodule status --recursive`：父仓注册了 9 个 package submodule；当前输出中除 `packages/duan-build` 外，多数 submodule 前缀为 `-`，说明可用性依赖当前本地工作树状态。
- `git ls-files` 与 `.gitignore` 检查：未发现已跟踪的 `target/`、`.duan/`、日志、tmp 或示例包 `Cargo.lock` 污染。Cargo 命令产生的嵌套 `target/` 与示例包锁文件当前均处于忽略状态。

## 主要问题

### 缺少跨 crate 聚合验证入口

问题定性：规范缺失导致风险。

证据：根 README 明确写明父仓是产品与文档集合，不默认作为 Cargo package 或根 workspace（`README.md:71`）；平台设计也要求在确有共享构建/发布流之前保持根目录不绑定 Cargo workspace 假设（`docs/platform-design.md:301`）。与此同时，仓库实际包含 `packages/duan`、`packages/duan-core`、`packages/duan-catalog`、`packages/duan-scenario`、`packages/duan-runner`、`packages/duan-build`、`packages/duan-cli`、`packages/duan-macros` 以及多组 `examples/packages/*`。

风险：根目录不是 workspace 本身不是问题，当前文档已经确认这是设计选择。问题在于没有等价的聚合验证脚本或清单，跨 facade、catalog、runner、CLI、generated runner 和示例包的变更无法用一个稳定入口复现本次逐包执行的 fmt、clippy、test、build、doc 检查，容易出现“只验证了当前 crate”的假结论。

建议：保留父仓非 workspace 的架构选择，同时补一个项目级验证入口，例如 `scripts/verify-rust.ps1` 或文档化的包清单，明确逐包执行顺序、覆盖范围、是否包含 examples，以及 `packages/duan-core` bench target 的处理方式。

### 生产 API 仍有 panic 和前置校验型 expect 边界

问题定性：违反硬性工程基线。

证据：`DomainContext` 在未声明读写组件时直接 `panic!`（`packages/duan-core/src/domain/context.rs:51`、`packages/duan-core/src/domain/context.rs:63`）；scheduler 的 `build` 会把 `try_build` 错误转成 panic（`packages/duan-core/src/runtime/scheduler.rs:168` 到 `packages/duan-core/src/runtime/scheduler.rs:169`）。`Package::collect(package_id: &str)` 对外接收字符串后用 `PackageId::new(package_id).expect("valid package id")`（`packages/duan-catalog/src/package.rs:125` 到 `packages/duan-catalog/src/package.rs:126`）。`duan-runner` 在 `plan_for_execution` 之后用 `expect("... factory was checked")` 获取 domain、reaction、entity factory（`packages/duan-runner/src/lib.rs:80` 到 `packages/duan-runner/src/lib.rs:103`）。

风险：这些路径不是纯测试代码。对于 CLI、Editor 或 generated runner 宿主，panic 会绕开结构化错误边界。`duan-runner` 的 `expect` 当前依赖前置校验，风险低于裸 `unwrap`，但调用链一旦重排或 registry 变成可变状态，错误会从 `RunnerResult` 泄漏成进程崩溃。

建议：把作者可触发的声明违规逐步前移到构建/注册/执行计划校验阶段，或者提供返回 `Result` 的安全路径。保留 panic 的内部断言需要写清楚不可恢复前提，并避免出现在 public-facing API 的主调用路径。

### `duan-catalog` 错误类型丢失 source

问题定性：建议优化。

证据：`duan-catalog` 手写 `PackageError`（`packages/duan-catalog/src/error.rs:8`），`ReadMetadata`、`ReadSchema`、`ParseSchema` 的 `source` 字段是 `String`（`packages/duan-catalog/src/error.rs:12` 到 `packages/duan-catalog/src/error.rs:30`）。对照 `duan-scenario` 已使用 `thiserror` 并保留底层错误类型。

风险：上层无法通过标准 `Error::source()` 获取 IO 或 parse 错误类型，CLI、Editor、测试断言和未来诊断分类只能依赖字符串。对于 catalog 这种位于 facade、runner、build 和 CLI 之间的基础 crate，错误边界会影响后续所有宿主。

建议：将 `duan-catalog` 错误类型迁移到 `thiserror` 或等价实现，保留 `std::io::Error`、serde/JSON parse error 等底层 source。对外展示文本可以继续保持当前文案，但内部错误链不要字符串化。

### `duan-runtime` 的 `debug-logs` feature 不表达真实可选能力

问题定性：规范缺失导致风险。

证据：`packages/duan-core/Cargo.toml` 中 `log` 是 optional dependency（`packages/duan-core/Cargo.toml:19`），但 `debug-logs = []` 没有启用 `dep:log`（`packages/duan-core/Cargo.toml:26` 到 `packages/duan-core/Cargo.toml:29`）。源码没有发现 `cfg(feature = "debug-logs")` 或实际 `log::` 调用；当前日志体系使用自有 `LogLevel`、`LogSink` 和 `LoggerHandle`。

风险：feature 名义存在，但无法改变构建产物或依赖图，也没有对应文档说明。后续调用方可能以为启用 `debug-logs` 会接入 `log` crate 或开启额外诊断，实际不会产生效果。

建议：二选一收口：如果 runtime 只保留自有诊断系统，删除 optional `log` 依赖和空 feature；如果要提供 `log` crate 适配，则让 `debug-logs` 或单独 feature 明确启用 `dep:log` 并补齐实现和测试。

### `cargo test --all-targets` 混入 Criterion bench 目标

问题定性：规范缺失导致风险。

证据：`packages/duan-core` 声明 `criterion` dev-dependency（`packages/duan-core/Cargo.toml:23`）和 7 个 `[[bench]]` target（`packages/duan-core/Cargo.toml:31` 到 `packages/duan-core/Cargo.toml:57`）。本次逐包执行 `cargo test --all-targets --all-features` 时，`packages/duan-core` 除单元测试和集成测试外，还运行了 `micro_*`、`runtime_world_bench`、`synthetic_pipeline_bench`、`world_step_bench` 的测试模式。

风险：测试门禁和性能基准边界混在一起，验证耗时和输出噪音都会增大。若后续 bench 数据规模扩大或 Criterion 行为变化，常规测试可能因为 bench target 耗时、环境依赖或管道输出问题而失真。

建议：在聚合验证入口中区分常规测试和性能基准。常规门禁可对 runtime 使用显式 `cargo test --lib --tests --all-features`，bench 回归另设 `cargo bench --bench world_step_bench` 或性能专项脚本。

### 文档入口存在迁移状态漂移

问题定性：违反项目已确认规范。

证据：`docs/README.md:15` 写着运行时文档位于 `packages/duan-core/docs/runtime/`，直到 runtime package 重命名为 `duan-runtime`。但当前 runtime package 已经是 `duan-runtime`（`packages/duan-core/Cargo.toml:2`），根 README 和 package naming 文档已经改成“package 已重命名，目录暂未改名”的口径（`README.md:73`、`docs/package-naming.md:33`）。

风险：入口文档把已完成的 package rename 写成未来条件，会误导维护者判断当前迁移状态。

建议：改成“runtime package 已是 `duan-runtime`，运行时文档暂仍位于 `packages/duan-core/docs/runtime/`，直到目录迁移完成”。

### 归档计划仍保留可执行指令语气和旧路径

问题定性：建议优化。

证据：`docs/archive/README.md` 说明 archive 只作历史上下文，不是当前设计权威；但 `docs/archive/plans/2026-05-15-duan-platform-completion.md:3` 仍保留 “For agentic workers: REQUIRED SUB-SKILL...” 这类可执行指令语气，且多处引用已迁移的 `packages/duan-package/**` 路径（同文件 `:35`、`:104`、`:168`、`:244`）。当前 `.gitmodules` 和 Cargo 事实已经是 `packages/duan-catalog`。

风险：文件虽然位于 archive，但保留强指令和未完成 checkbox，容易被后续 agent 或维护者误当成当前执行计划。

建议：在该归档计划头部补充明确 stale 标记，说明当前权威入口是 `docs/platform-design.md`、`docs/package-naming.md` 和当前 Cargo 文件；必要时弱化或删除执行性指令语气。

## 整改优先级建议

### 第一阶段：补齐项目级验证入口

- 新增或文档化跨 crate 验证入口，复现本次逐包 fmt、clippy、test、build、doc 的覆盖范围。
- 在验证入口中明确 examples 是否纳入、`packages/duan-core` bench target 是否纳入常规 test、性能基准用哪个命令单独跑。

### 第二阶段：收紧错误边界

- 优先处理 `DomainContext`、scheduler、`Package::collect` 和 `duan-runner` factory 获取路径，把作者/场景可触发错误纳入结构化 `Result`。
- 将 `duan-catalog` 错误类型迁移为可保留 source chain 的实现。

### 第三阶段：清理漂移配置和文档

- 收口 `duan-runtime` 的 `debug-logs` feature 与 optional `log` 依赖。
- 修正 `docs/README.md` 的 runtime package/目录迁移描述。
- 给归档计划补 stale 标记，避免 archive 中的旧路径和执行指令继续影响当前工作流。
